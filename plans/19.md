# Issue #19: Postgres dialect support in packages/db (SQLite preserved)

## Goal

Make `packages/db` dialect-aware so the web app can run on Neon Postgres (Vercel)
while local SQLite mode keeps working unchanged. Selected at runtime by `DB_DIALECT`
(`sqlite` default, `postgres` opt-in). Search must return correct results on both
dialects (FTS5 stays SQLite-internal; Postgres uses a tsvector/ILIKE equivalent
behind the search router).

## Key facts from investigation

- `packages/db/src/client.ts` hard-throws unless `DB_DIALECT === "sqlite"`.
- `packages/db/src/schema.ts` defines sqlite tables (skills, variations, favorites,
  compositions, config). Consumed via `@curiouslycory/db/schema` by many API routers
  and `disk-sync`, all through the drizzle query builder (`.select`, `.insert`,
  `.query.skills`, etc.) which is dialect-portable *as long as the table objects
  match the active db dialect*.
- The ONLY sqlite-specific production call is `ctx.db.all<T>(sql\`...\`)` in
  `packages/api/src/router/search.ts` (raw FTS5 query). Everything else is portable.
- `test-utils.ts` builds an in-memory better-sqlite3 db + `initFTS`; the search test
  mocks `@curiouslycory/db/client` only (not `@curiouslycory/db` or `/schema`).
- Drizzle-kit sqlite config lives at `packages/db/drizzle.config.ts` with
  `tablesFilter: ["!skills_fts*"]`. `pnpm db:push` -> `drizzle-kit push`.
- `@neondatabase/serverless@0.10.0` is already resolved in the lockfile as a drizzle
  peer. Need to add it as a direct dep of `packages/db`.
- README already references `POSTGRES_URL` for the Vercel deploy path.

## Design

### Schema (dialect-portable table objects)

- Move current sqlite tables into `src/schema.sqlite.ts` (byte-for-byte same defs).
- Add `src/schema.pg.ts`: pgTable mirrors (text/timestamp/pg defaults, same column
  names and constraints).
- `src/schema.ts` becomes a runtime switch that re-exports the active dialect's tables
  with a single **static** type (the sqlite type) via one localized `as unknown as`
  cast at the module boundary. Consumers stay dialect-agnostic and typecheck against
  the stable sqlite types; at runtime with `DB_DIALECT=postgres` they operate on pg
  tables, producing correct pg SQL.

### Client factory (`src/client.ts`)

- `const dialect = DB_DIALECT ?? "sqlite"`.
- `sqlite` branch: existing better-sqlite3 path, byte-for-byte unchanged (mkdir, WAL,
  `initFTS`, `drizzle({ client, schema: sqliteSchema })`).
- `postgres` branch: `drizzle` from `drizzle-orm/neon-http` with `neon(POSTGRES_URL)`
  and `schema: pgSchema`; no FTS init.
- Remove the hard-throw. Export `db` typed as `Database` (the sqlite drizzle type);
  the pg client is cast `as unknown as Database` so all consumers/routers keep one
  stable type. Also export `dbDialect`.
- `src/types.ts`: `export type Database = BetterSQLite3Database<typeof sqliteSchema>;`
  and `export type DbDialect = "sqlite" | "postgres";`.

### Search abstraction (`src/search.ts`)

- Export `searchSkills(db, params, dialect?)` -> `SkillSearchResult[]`. Encapsulates:
  - empty query -> drizzle `.select()` (portable), snippet null.
  - dialect `sqlite` -> existing FTS5 `db.all<T>(sql\`...\`)` logic, unchanged.
  - dialect `postgres` -> tsvector/ILIKE via `db.execute(sql\`...\`)`:
    `to_tsvector('english', name||description||tags||content) @@ plainto_tsquery`,
    `ts_rank` ordering, `ts_headline(...)` for the `<mark>` snippet; category filter.
  - `dialect` defaults from `DB_DIALECT` env so the router stays dialect-agnostic and
    the existing client mock in the search test is unaffected.
- `packages/api/src/router/search.ts` becomes a thin caller: `searchSkills(ctx.db, input)`.
- Export `searchSkills` + result type from `src/index.ts`.

### Migrations / scripts

- Keep sqlite `drizzle.config.ts` + `push` script unchanged (default path preserved).
- Add `drizzle.pg.config.ts` (dialect `postgresql`, schema `./src/schema.pg.ts`,
  `dbCredentials.url = POSTGRES_URL`, out `./drizzle/pg`).
- Add scripts: `push:pg`, `generate:pg`, `migrate:pg` (each `with-env`).
- Generate the initial pg migration into `drizzle/pg` and commit it.
- Add `POSTGRES_URL` to `.env.example` and `turbo.json` globalEnv.
- Document per-dialect `db:push` in README.

## Tests

- `packages/db/src/__tests__/client.test.ts`: default dialect is sqlite when unset;
  `dbDialect` reflects env; factory does not throw for `postgres`.
- `packages/db/src/__tests__/search.test.ts`: pg branch genuinely exercised with a
  fake `{ execute }` db — asserts tsvector SQL is issued and rows map to the correct
  camelCase `SkillSearchResult` shape (incl. `<mark>` snippet, Date conversion).
  No live pg required. Optionally a live-pg gated test behind `TEST_POSTGRES_URL`.
- Existing `packages/api` search tests must stay green unchanged (sqlite path).

## Review notes for orchestrator (#27 deploy)

- Postgres uses on-the-fly `to_tsvector`/`ts_headline`; correct but unindexed. A
  follow-up can add a GIN index / generated tsvector column for scale.
- `pnpm db:push` stays sqlite; deploy must run the pg path
  (`DB_DIALECT=postgres POSTGRES_URL=... pnpm --filter @curiouslycory/db push:pg`
  or the committed migrations via `migrate:pg`).
