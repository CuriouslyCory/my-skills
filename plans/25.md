# Plan #25: Install personal library via `@me/<name>` (+ `ms apply` cloud sources)

Let an authenticated user install their personal agents/skills from their cloud
library. Add a `cloud` source type recognized as `@me/<name>` (and `@me` to
browse), backed by `library.list`/`library.get` tRPC procedures, installed
through the existing pipeline (installer, adapters, manifest entry, content
hash). Wire `cloud` sources into `ms apply`, `ms update`, and `ms check`.

## Design

### 1. `cloud` source type + parsing

- `packages/shared-types/src/index.ts`: add `"cloud"` to `SourceTypeSchema`
  (`["github", "gitlab", "url", "local", "cloud"]`).
- Add optional `category: ArtifactCategorySchema.optional()` to
  `SkillEntrySchema` so cloud entries record their deploy category
  (skill/agent/prompt/claudemd). Backward compatible (optional).
- `apps/cli/src/services/source-parser.ts`: add `CloudSource`
  (`{ type: "cloud"; name: string | undefined }`) to the `SkillSource` union.
  `parseSource` recognizes `@me` (browse all -> `name: undefined`) and
  `@me/<name>` (-> `name`). The `@me` check runs BEFORE the shorthand regex so
  `@me/foo` is not misparsed as `owner/repo`. Export `cloudSourceName(source)` to
  recover `<name>` from a manifest `source` string (`@me/<name>` -> `<name>`).

### 2. `library` tRPC router (`packages/api/src/router/library.ts`)

Both `protectedProcedure`, per-user scoped via `ctx.session.user.id`.

- `library.list({ category? })`: the caller's artifacts across all categories,
  metadata only (id, name, description, category, tags, author, version,
  updatedAt) ordered by updatedAt desc. No content (light payload for browsing).
- `library.get({ name })`: the caller's single artifact by unique
  (userId, name), full content + metadata, or `null`.

Register as `library: libraryRouter` in `packages/api/src/root.ts`.

### 3. CLI cloud-source service (`apps/cli/src/services/cloud-source.ts`)

Shared by add/apply/update/check. Keeps the type-only `AppRouter` import intact
(reuses `createApiClient`), so no server runtime enters the CLI bundle.

- `createCloudClient()`: loadConfig + loadCredentials, resolveServerUrl,
  resolveToken. Throws `AuthRequiredError` with a clear message
  ("Not logged in. Set MY_SKILLS_TOKEN or run `ms login` ...") when no token.
- `listCloudLibrary(client)` / `fetchCloudArtifact(client, name)` (throws a clear
  "not found in your library" error on null).
- `normalizeCategory(category)`: string|null -> ArtifactCategory (fallback skill).
- `cloudDeployDir(projectRoot, category)`: `join(projectRoot, DEPLOY_PATH_MAP[category])`.
- `cloudManifestSource(name)`: `@me/<name>`.
- `materializeCloudArtifact(artifact)`: writes a temp `<tmp>/<name>/SKILL.md`
  (via `buildSkillContent`, deterministic so hashes are stable across runs),
  returns `{ resolved: ResolvedSkill, category, cleanup }`. Install reuses
  `installSkill` (cp + `computeSkillHash`) exactly like github/local.

### 4. `ms add @me/<name>` / `ms add @me` (`apps/cli/src/commands/add-cloud.ts`)

New file; add.ts only gains an import + a 3-line dispatch branch after
`parseSource` (keeps the favorite-flag logic untouched for a clean #24 merge).

- `addFromCloud(cloud, opts, config, manifest, projectRoot, agents)`:
  builds the client (AuthRequiredError -> clear error, exit 1), lists the
  library. `@me/<name>` -> install that one. `@me` -> `--list` prints, `--yes`/
  `--skill '*'` installs all, else an interactive `checkbox` picker (reuses the
  existing interactive list UX). Installs each via `installSingleCloudArtifact`
  (materialize -> `installSkill` into `DEPLOY_PATH_MAP[category]` -> manifest
  entry `sourceType: "cloud"` + `category` + computed hash -> adapters).

### 5. `ms apply` cloud handling (`apps/cli/src/commands/apply.ts`)

- `resolveEntrySkill` returns `{ resolved, cleanup? }`; adds a `cloud` branch
  (createCloudClient -> fetch -> materialize). AuthRequiredError propagates and
  is caught by the existing per-entry try/catch -> `action: "failed"` with the
  clear message; other entries still apply. Failure count drives the exit code
  (non-hook: 1; hook: 0), matching #18's scheme. Partial failure reflected.
- Cloud entries reconcile against `DEPLOY_PATH_MAP[category]` (not skillsDir) via
  `cloudEntryTargetDir(entry, projectRoot)`; github/local unchanged. In-sync
  cloud entries are a hash-only noop (no token needed, fully offline).

### 6. `ms update` / `ms check` cloud handling

- `update.ts` `updateSingleSkill`: cloud branch mirrors github (materialize,
  install into category target, compare hash, persist). No token -> failed with
  clear message.
- `check.ts` `checkSingleSkill`: cloud branch fetches + materializes + hashes +
  compares over the API; no token -> "remote unavailable" with a login hint.

### 7. Unauthenticated `@me/...`

`AuthRequiredError` (#23) is the single clear "run `ms login`" signal across add
(printed, exit 1), apply/update (per-entry failure), and check (remote
unavailable + hint).

## Tests

- `source-parser` cloud cases (`@me`, `@me/<name>`, `cloudSourceName`).
- `library` router per-user scoping (list/get return only the caller's rows).
- `add-cloud`: installs a `cloud` manifest entry with category + hash; interactive
  `@me` picker; unauth -> clear error. API mocked.
- `apply`: cloud entry applies with a token; without a token fails-clearly while
  other entries still apply (partial-failure exit).
- `check`/`update`: cloud hash change detected over the (mocked) API.
